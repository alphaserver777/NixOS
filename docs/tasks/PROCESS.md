# Процесс работы с задачами

## Принцип

**Сначала spec, потом реализация.**

Любое нетривиальное изменение конфигурации начинается с task spec.
«Нетривиальное» — это всё, что:
- затрагивает shared-модули (`nixos/modules/`)
- меняет конфигурацию production-хоста (`x-disk`, серверы)
- вводит новый инструмент или сервис
- имеет неочевидный rollback

Мелкие правки (исправление опечатки, добавление одного пакета в
`local-packages.nix`) можно делать без spec, но с честным commit-сообщением.

---

## Жизненный цикл задачи

```
1. ОБЯЗАТЕЛЬНЫЙ ЧЕКЛИСТ
   Перечитай: WORKFLOW.md, constitution.md, architecture.md, devplan.md
   + DEPLOYMENT.md (если задача касается deploy)
   + связанные task specs

2. СОЗДАНИЕ SPEC
   Скопируй TEMPLATE.md → docs/tasks/NNN-короткое-название.md
   Заполни все разделы. Status: "draft" или "ready"

3. РЕАЛИЗАЦИЯ
   Status → "in progress"
   Изменения — в ветке develop (или feature-ветке)
   Фиксируй промежуточные коммиты

4. VERIFICATION
   Проверь каждый пункт из раздела "Acceptance Criteria"
   Выполни шаги из раздела "Verification"
   Только после этого → Status: "done"

5. ОБНОВЛЕНИЕ ДОКУМЕНТАЦИИ
   Если изменилась архитектура → обнови architecture.md
   Если закрыт пункт devplan → обнови devplan.md
   Если появился follow-up → создай новую задачу

6. КОММИТ И МЕРЖ
   Commit от чистого рабочего дерева
   PR из develop → main (или прямой merge для мелких задач)
```

---

## Нумерация задач

Формат: `NNN-короткое-описание.md`

- `NNN` — трёхзначный номер, начиная с `001`
- Описание — 2-4 слова через дефис, без пробелов
- Примеры: `001-nix-ld-deploy.md`, `002-tailscale-clarify.md`,
  `003-docker-opt-in.md`

Следующий доступный номер: **002**

---

## Статусы задачи

| Статус | Описание |
|---|---|
| `draft` | Spec написан, не готов к реализации |
| `ready` | Spec готов, ждёт реализации |
| `in progress` | Реализация идёт |
| `done` | Verification пройден, задача закрыта |
| `blocked` | Есть внешний блокер, зафиксирован в "Заметки" |
| `cancelled` | Задача отменена, причина в "Заметки" |

---

## Follow-up правило

Если в процессе реализации обнаружилась новая проблема или необходимость —
создай **новую задачу**. Не расширяй текущую задачу за пределы её scope.

Это предотвращает превращение одной задачи в бесконечный клубок изменений.

---

## Что писать в commit-сообщении

```
<тип>: <что сделано>

Closes: docs/tasks/NNN-название.md
```

Типы: `feat`, `fix`, `refactor`, `docs`, `chore`

Пример:
```
feat: добавить nix-ld для запуска dynamically-linked бинарей

Closes: docs/tasks/001-nix-ld-deploy.md
```

## Правило для LLM

Перед созданием новой задачи (**перед написанием spec**):
1. Прочитай `docs/WORKFLOW.md`
2. Прочитай `docs/constitution.md`
3. Прочитай `docs/architecture.md`
4. Прочитай `docs/devplan.md`
5. Прочитай `docs/tasks/PROCESS.md` (этот файл)

Перед началом реализации задачи — то же самое плюс сам spec задачи.

Это обязательно, не опционально.
