# Конституция проекта

Инженерные правила, обязательные для всех изменений в репозитории.
Нарушение этих правил без явного task spec недопустимо.

---

## Source of Truth

| Что | Где |
|---|---|
| Список хостов и их stateVersion | `nixos-config/flake.nix` → `hosts` |
| Конфигурация хоста | `nixos-config/hosts/{hostname}/configuration.nix` |
| Общие desktop-модули | `nixos-config/nixos/modules/default.nix` |
| Серверные модули | `nixos-config/nixos/modules/server/default.nix` |
| Конфигурация пользователя | `nixos-config/home-manager/home.nix` |
| Пакеты пользователя (общие) | `nixos-config/home-manager/home-packages.nix` |
| Пакеты хоста (частные) | `nixos-config/hosts/{hostname}/local-packages.nix` |
| Секреты | `nixos-config/secrets.nix` или `$NIXOS_SECRETS_PATH` |

Если что-то не задокументировано — это не значит, что это не существует.
Ищи source of truth по таблице выше, а не по README.

---

## Правила изменения модулей

### 1. Shared-модули — с осторожностью

`nixos/modules/default.nix` импортируется всеми desktop-хостами (`Huawei`,
`x-disk`, `main`). Изменение в любом файле, включённом в этот список,
**автоматически затрагивает все эти хосты**.

Перед добавлением нового модуля в `default.nix`:
- Убедись, что модуль безопасен для всех хостов-импортёров
- Если модуль нужен только одному хосту — используй `lib.mkIf (hostname == "...")`
  внутри модуля, или добавляй его только в конкретный `hosts/{hostname}/configuration.nix`

### 2. Серверные модули — отдельный scope

`nixos/modules/server/` — отдельный набор для серверных хостов. Не смешивай
с desktop-набором без явной причины, зафиксированной в task spec.

### 3. Новый модуль — новый файл

Не добавляй новую логику в существующий модуль, если она концептуально
отдельная. Один файл — одна ответственность.

---

## Правила по секретам

- **Никогда** не хардкодь секреты (URL, токены, пароли) в `.nix`-файлах
- Секреты → только через SOPS: `nixos-config/secrets/`
- Fallback через env: `$NIXOS_SECRETS_PATH` (см. `flake.nix`)
- `secrets.nix` не коммитить в публичный репозиторий

---

## Правила по nixpkgs

- Текущий канал: `nixos-25.05`. Изменение канала — отдельная задача с
  полным тестированием всех хостов.
- Unfree-пакеты разрешены только для явно перечисленных в `flake.nix`:
  `rustdesk`, `libsciter`, `libsciter-4.4.8.23-bis`.
  Добавление нового unfree-пакета требует обновления `allowedUnfreeNames`.
- `permittedInsecurePackages` — крайняя мера. Используется только если нет
  альтернативы. Текущий исключение: `beekeeper-studio-5.1.5` на `x-disk`.

---

## Правила по Home Manager

- Конфигурация пользовательского окружения (`~/.config/`, dotfiles) —
  **только через Home Manager**, не через imperativeные изменения вручную.
- Пакеты, нужные пользователю (а не системе) — в Home Manager, не в
  `environment.systemPackages`.
- Исключение: пакеты, которые нужны до старта graphical session или в scope
  системных сервисов.

---

## Правила по schema change / rollback

- Любое изменение, которое меняет структуру файлов (`/etc/`, сервисы systemd)
  или данных (`Samba shares`, `Syncthing`), должно иметь явный rollback-план
  в task spec.
- Перед применением: убедись, что предыдущая конфигурация доступна через
  `nixos-rebuild switch --rollback` или известен предыдущий commit.
- Изменение `stateVersion` — необратимо. Требует отдельной задачи и явного
  подтверждения.

---

## Verification — обязательна

Задача не считается завершённой, пока не выполнены все пункты секции
`Verification` из её task spec.

Минимальная проверка для любого изменения конфигурации хоста:
```bash
# Проверка синтаксиса без применения
nixos-rebuild dry-build --flake .#<hostname>

# Применение и проверка
sudo nixos-rebuild switch --flake .#<hostname>
```

## Запрещено

- **Скрытые заглушки и временные хаки** без task spec и комментария в коде
  с номером задачи. «Временное» без фиксации — навсегда.
- **Закомментированный код** без объяснения. Если не нужен — удали.
  Исключение: `# ./tailscale.nix` в `default.nix` — временно отключён,
  причина должна быть в task spec или комментарии.
- **Изменение конфигурации production-хоста** без предварительного тестирования
  на `Huawei` или VM.
- **Deploy из dirty working tree** (незакоммиченные изменения).
- **Хардкод hostname-а** в shared-модуле без `lib.mkIf` — используй
  условный guard или выноси в host-specific конфиг.

## Что такое «production» в этом репозитории

_Предположение:_ `x-disk` — основная рабочая машина с ценными данными,
Samba-шарой и rsyslog-форвардингом. Её выход из строя — ощутимая проблема.

`srv-home-min` — сервер с Docker; на нём, вероятно, работают сервисы.

Остальные хосты — менее критичны, но `Huawei` (ноутбук) — основное рабочее
устройство.
