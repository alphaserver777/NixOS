# Рабочий процесс (SDD)

## Зачем эта система

Репозиторий управляет **6 NixOS-хостами** через общие модули. Изменение файла в
`nixos/modules/` мгновенно затрагивает все машины, которые его импортируют.
Без явного контроля — сломанный хост, который ты не проверял.

Эта документационная система гарантирует:
- Каждое нетривиальное изменение описано в **task spec** до реализации
- Acceptance criteria проверяются явно, а не «ну, скорее всего работает»
- Архитектурные решения фиксируются в документах, а не тонут в commit-сообщениях
- Следующий LLM-сеанс стартует с полным контекстом, а не с нуля

## Ключевые документы

| Документ | Содержание |
|---|---|
| `docs/WORKFLOW.md` | **Этот файл.** Процесс работы. |
| `docs/constitution.md` | Инженерные правила. Что нельзя делать никогда. |
| `docs/architecture.md` | Топология хостов, структура модулей, source of truth. |
| `docs/devplan.md` | Среднесрочный план развития. |
| `docs/DEPLOYMENT.md` | Как применять конфиги на каждый хост. |
| `docs/tasks/PROCESS.md` | Как создавать и вести задачи. |
| `docs/tasks/TEMPLATE.md` | Шаблон task spec. |

## ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ДЛЯ LLM

**Перед созданием новой задачи** и **перед началом реализации** необходимо
прочитать:

1. `docs/WORKFLOW.md` — этот файл
2. `docs/constitution.md` — что нельзя нарушать
3. `docs/architecture.md` — как устроена система
4. `docs/devplan.md` — куда движется проект
5. Если задача касается deploy/infra → `docs/DEPLOYMENT.md`
6. Связанные task specs из `docs/tasks/`

Это не формальность. Без этого контекста легко сломать хост, который «не был
в фокусе».

## Жизненный цикл изменения

```
Идея / проблема
    ↓
Task spec (docs/tasks/NNN-название.md)
    ↓
Реализация (с регулярным сохранением прогресса)
    ↓
Verification по Acceptance Criteria из task spec
    ↓
Обновление docs (architecture.md / devplan.md если нужно)
    ↓
Commit → ветка develop → PR → main
```

Не начинай реализацию без task spec.
Не закрывай задачу без явной проверки Acceptance Criteria.

## Правила ветвления

| Ветка | Назначение |
|---|---|
| `main` | Стабильная конфигурация, применённая на хостах |
| `develop` | Текущая разработка |
| `hotfix` | Срочные исправления, которые нельзя откладывать |
| Feature-ветки | По необходимости, именовать `feature/описание` |

## Правила deploy

- **Shared-модули** (`nixos/modules/default.nix`) применяются ко всем
  desktop-хостам одновременно. Не меняй их без проверки.
- Перед применением к `x-disk` или другому production-хосту — проверь на
  `Huawei` или поднятой VM.
- Deploy идёт только от зафиксированного commit (не от dirty working tree).
- Всегда держи под рукой команду rollback — см. `docs/DEPLOYMENT.md`.
- **Germany VDS** (`64.188.64.23`) — вне управления этого репозитория.

## Работа с LLM-сессиями

В начале каждой новой сессии:
1. Прочитай этот файл
2. Прочитай `docs/architecture.md`
3. Прочитай task spec задачи, над которой работаешь

Если задача ещё не создана — создай её по шаблону `docs/tasks/TEMPLATE.md`
прежде чем писать код.
